# 路线图

> 本项目现在处在**设计期**。这一期的目标不是"能跑起来"，而是
> **"说得清楚、且说得出矛盾"**——每种制品的字段、枚举、关系都能被机器检查，
> 改一处不会漏三处。

---

## 设计期（当前）

### 目标

* 把 35 种制品的**定义**补齐到可实现的程度：字段有类型有约束，枚举有全集，
  子结构有字段表，关系有出处。
* 让制品体系成为**唯一事实来源**：图、清单、主线、文档全部从定义文档生成。
* 把体系讲清楚：任何人都能在一个网页里看完 35 种制品是什么、为什么存在、彼此怎么连。

### 验收标准

* **完整性** —— 35 种制品各有一份定义文档，每份都解析得出字段表与关系表，
  没有"预留"章节、没有空枚举。
* **一致性** —— 每种制品恰好属于一个主线阶段；每条主线交接都是真实存在的关系边；
  横切阶段只准备、不产出。
* **可读性** —— 前端能展示：体系图（35 节点 / 90 边）、开发主线（10 + 3 阶段）、
  每种制品的完整字段表，以及全部设计文档。
* **可追溯** —— 制品之间只有 typed ID 引用，没有裸字符串引用；
  每条关系边都能指回声明它的那张表。

### 当前进度

| 验收项 | 状态 |
|--------|------|
| 完整性 | ⚠️ 主体完成，`Requirement` 的 EARS/SVO 模式字段、`Process` 的 `Forbidden` 仍是预留 |
| 一致性 | ✅ 构建脚本 + 测试双重校验 |
| 可读性 | ✅ 概览 / 体系图 / 主线 / 制品 / 文档 五个视图 |
| 可追溯 | ⚠️ 引用格式统一了，但"目标制品必须存在"还没有校验规则 |

## 实现期（尚未开始）

设计定稿后再启动。这里保留最初的验收标准，作为实现期的目标锚点。

### Stage 1：一个需求的命令行工具

* 尽量覆盖命令行工具开发的全生命周期，为后续项目自举提供基础
* 确保流程是严格的
* 确保每个制品最小化，只包含必要的信息
* 确保每个制品都是可验证的

**验收标准**：1 个新需求，完整实现一个命令行工具。

### Stage 2：两个需求的命令行工具

* 项目里的某些制品可能需要修改，而不是一步到位
* 修改可能会级联地导致其他制品的修改

**验收标准**：多个新需求，完整实现一个多子命令的命令行工具。
